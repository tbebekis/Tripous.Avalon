# Generation Workflow

Automatic declaration is a repeatable workflow.

The developer edits schema and metadata.

The Registration Builder regenerates C# declaration files.

The application then compiles those files like normal source code.

## Workflow Summary

The usual flow is:

- edit the current `Schema.sql` file
- add or adjust metadata comments
- run `RegBuilderConsole`
- review the generated C# diff
- keep manual extensions outside generated files
- rebuild or test the application when needed

```text
Schema.sql
    -> metadata comments
    -> RegBuilderConsole
    -> generated C# files
    -> application registry
```

## Edit The Schema

The schema file is the source of truth for automatic declaration.

Changes belong there when they affect:

- tables
- fields
- foreign keys
- lookup metadata
- locator metadata
- module metadata
- form metadata
- filters
- field groups
- code providers

Example:

```sql
/*---------------------------------------------------
Table: Product
Module: Product ProductDataModule
Group: Inventory
Form: Product ProductForm
FilterFields: Code, Name, ProductGroup__Name
IsLookup
----------------------------------------------------*/
CREATE TABLE {TableName} (
    Id @NVARCHAR(40) @NOT_NULL primary key,
    Code @NVARCHAR(40) @NOT_NULL,          -- Code PRD-YYYY-XXXXXX
    Name @NVARCHAR(96) @NOT_NULL,
    ProductGroupId @NVARCHAR(40) @NULL,    -- Lookup
    ProductGroupName @NVARCHAR(96) @NULL,  -- Snapshot ProductGroup.Name

    FOREIGN KEY (ProductGroupId) REFERENCES ProductGroup(Id)
    )
```

## Database Impact

Schema changes may require database recreation.

Examples:

- adding fields
- removing fields
- changing field types
- changing constraints
- changing foreign keys

During development and sample application work, the usual approach is often to delete and recreate the database after such changes.

Generated schema and registry code describe the application structure.

They do not automatically migrate existing application data.

Tripous has `SqlProvider.CreateDatabase()` support for providers that can create a database from a connection string.

Currently this is supported by:

- SQLite
- SQL Server
- MySQL
- PostgreSQL
- Firebird

It is not supported by:

- Oracle

When the provider supports database creation, Tripous can recreate the database depending on the connection settings, file path, server permissions and application startup logic.

For providers that do not support `CreateDatabase()`, or when permissions/settings do not allow it, the developer must recreate the database manually.

That may mean dropping tables, deleting the database file, or using the database administration tools of the selected RDBMS.

## Run The Builder

From the repository root, TinyERP version 2 can be regenerated with:

```text
dotnet run --project Tools/RegBuilderConsole -- --project tERP.Version2
```

When configured assemblies are already current:

```text
dotnet run --project Tools/RegBuilderConsole -- --project tERP.Version2 --no-build
```

The console tool:

- builds configured projects unless `--no-build` is used
- loads configured assemblies
- runs the Registration Builder
- generates files in a temporary folder
- copies generated `.cs` files to the configured output folder

For TinyERP, generated files are copied to:

```text
SampleApps/TinyERP/tERP.Data/Registry
```

## Generated Files

Generated files contain an auto-generated header.

```text
<auto-generated>
This file was generated by Tripous RegBuilder.
Do not edit this file manually.
</auto-generated>
```

Do not manually edit generated files.

When generated output is wrong or incomplete, change the schema metadata and run the builder again.

## Review The Diff

After generation, review the changed generated files.

The review should answer:

- did the expected schema version file change?
- did the expected registry version file change?
- did modules, forms, lookups and locators update as expected?
- did code provider seed statements change as expected?
- did unrelated generated files change?

Unexpected generated changes usually mean the schema metadata changed more broadly than intended.

## Manual Extensions

Generated code is only the structural declaration.

Manual application behavior belongs outside generated files.

Use handwritten files for:

- custom data module behavior
- custom form behavior
- custom locator configuration
- services
- validators
- document posting logic
- sample data
- tests

The generated files may reference those handwritten classes by name.

The class implementation remains normal application code.

## Versioned Workflow

Applications may have multiple versions.

TinyERP uses:

- `Schema01.sql`
- `Schema02.sql`
- `RegistryVersion1`
- `RegistryVersion2`
- `SampleData.Version1`
- `SampleData.Version2`

New schema work is added to the current version strategy of the application.

Previous schema files may be passed as reference files so the builder can understand existing tables and relationships.

## Practical Rule

Treat automatic declaration as source generation.

The maintained source is:

- schema files
- metadata comments
- handwritten extension classes

The generated registry files are output.

They are committed, but they are not edited by hand.
